# Механика сетевого обмена в МП: транспорт, качество, потери, компенсации

Документ отвечает на вопрос «как контролируется качество связи и что происходит при потерях».
Всё перечисленное — реализованный код (`backend/src/index.ts`, `backend/src/servers/roomServer.ts`,
`backend/src/services/matchState.ts`, `frontend/src/stores/multiplayerStore.ts`), а не план.

## 1. Транспорт

- Один WS-конншн на клиента: `wss://…/ws` (nginx → контейнер, `noServer` + ручной `upgrade`
  в `index.ts`). Стек: WebSocket поверх WSS поверх **TCP**. TCP сам ретранслирует потерянные
  сегменты, поэтому на прикладном уровне «потерянного сообщения» обычно нет — есть **задержка**:
  потеря превращается в спайк RTT, а не в дырку в потоке.
- Рамка входящего сообщения ограничена `MP_MAX_PAYLOAD` = 16 КиБ; всё остальное — `bad_message`.
- Честной нумерации кадров TCP в приложении нет: порядок соблюдаем сами (см. §4).

## 2. Контроль живости (two-level heartbeat)

| Уровень | Кто шлёт | Интервал | Что делает |
|---|---|---|---|
| WS protocol ping/pong (`ws`) | сервер | `MP_TRANSPORT_PING_MS` = 30 с | браузер отвечает на ping **автоматически**, без JS; нет pongа за цикл → `terminate()` |
| app-level `ping`/`pong` | клиент | `MP_CLIENT_PING_MS` = 25 с | держит nginx-idle (60 с) и даёт **оценку часов** |

Держать соединение «на глазке» по 60 с nginx → 30-секундный серверный ping. Серверный ping
не доходит ровно по той же причине, что и любой кадр: это настоящая потеря на канале, и она
считается (см. §5).

## 3. Часы и порядок старта

- `pong { serverTs }` → клиент хранит `clockOffset = serverTs − Date.now()` (оценка, точность ±RTT/2).
- Отложенная мусорка планируется сервером по **своим** часам (`applyAt`), клиент ставит таймеры
  по смещённым. Итог: ряд мусора приходит в один и тот же момент серверных часов у обеих сторон,
  расхождение ограничено половиной RTT.
- Старт раунда: `game_start { startTime }` + общая задержка `MP_START_DELAY_MS` (2 с) — обе
  стороны начинают по серверному времени, а не по факту получения широкого сообщения.

## 4. Целостность игрового потока (то, что реально ломается при плохой связи)

- Каждый зал (lock) клиентского движка имеет `globalStep` — сквозной счётчик **своего** игрока,
  инкрементируется ровно один раз на зал.
- Сервер держит на каждый матч реплей `MatchState` и требует строгой последовательности шагов
  (`step N+1`). Проверка независима от того, что прислал другой игрок.
- Компенсации потерь:
  1. **Буфер неотправленных** `unsentLocks` (клиент): залы, отправленные при закрытом сокете,
     сохраняются и пересылаются по порядку сразу после реjoin.
  2. **Кольцо отправленных залов** `reportedLocks` (клиент, 80 последних кадров).
  3. **`resync_request`** (сервер): если шаг пришёл вперёд на 1…`MP_RESYNC_MAX_GAP` (12), сервер
     не считает это читерством — он просит дослать недостающее и ждёт `MP_RESYNC_GRACE_MS` (3 с).
     Клиент досылает из кольца по порядку. Только если досыла нет — `invalid_move` + forfeit.
     На матч даётся `MP_RESYNC_MAX_PER_MATCH` (3) таких эпизода.
- Потерянные залы **не** пересылаются «по таймауту» молча: сервер всегда видит дырку и либо чинит
  её запросом, либо заканчивает матч. Тихого расхождения досок быть не может.

## 5. Учёт потерь и качества (измеряется, а не подразумевается)

- Сервер на каждом сокете ведёт счётчики прикладных кадров: `msgsIn/msgsOut/bytesIn/bytesOut`
  (инкременты в `onMessage` и в `send`).
- Транспортный heartbeat даёт `pingsSent`, `pingsLost` (пинг, на который не пришёл pong до
  следующего пинга — это и есть потерянный кадр канала) и `lastPongRttMs`.
- Всё это отдаётся клиенту в `conn_test_ack`. Клиентский «Тест связи» в комнате шлёт 12 кадров
  `conn_test` с шагом 150 мс и считает: отправлено / получено / потеряно, RTT min/avg/max,
  дёрганье (среднее абсолютное отклонение) + серверные счётчики. Кнопка: комната → «Тест связи».

## 6. Разрыв связи и возвращение

- Сокет упал → сервер держит место `MP_REJOIN_GRACE_MS` = 120 с, остальным сразу шлётся
  `opponent_dropped { returnBy }`.
- Клиент переподключается с экспоненциальной задержкой (1 с → ×1.5 → до 8 с) и делает `rejoin_room`
  с токеном места. Токен живёт в **sessionStorage** (на вкладку): две вкладки одного браузера
  больше не перехватывают друг у друга место.
- Если реjoin не принят (`bad_token`/`room_not_found`) — клиент честно сбрасывает комнату и
  показывает код потерянной комнаты, а не мёртвый ростер с немым чатом.
- Перезагрузка страницы посреди матча = честный технический forfeit (состояние стакана не
  восстановить); обрыв сокета при живом движке = возобновление без обвинений.

## 7. Ограничения честности (античит) и лимиты

- Сервер не доверяет ни одному текстовому/цифровому полю: имена нормализуются, чат режется,
  payload'ы проверяются по форме, каждый зал перепроверяется реплеем (доска, куски, линии,
  поддержка, мусорные ряды).
- Rate limit: `MP_MSG_MAX_PER_SEC` = 60 кадров/с на сокет, чат — 1 сообщение / `MP_CHAT_COOLDOWN_MS`
  (500 мс), быстрые фразы — 1 / 3 с. Нарушение протокола (> `MP_MAX_VIOLATIONS` = 30) → разрыв.
- Все нарушения протокола пишутся в лог матча как `protocol_violation` (раньше — не писались
  вообще, что и мешало разбирать EX8H).

## 8. Диагностика

- Каждый матч: append-only JSONL в `backend/data/mp-matches/` (`match_start`, `piece_lock`,
  `garbage_delivered`, `resync_requested/failed`, `protocol_violation`, `socket_closed`,
  `match_over`, `match_closed`).
- Чтение: `GET /api/mp/matches[/:file|/:file/replay]?token=…` (`npm run mp:logs`), офлайн-реплей:
  `npm run mp:replay -- <file>`.
