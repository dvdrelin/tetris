## 1. Что есть сейчас (проверено по коду)

### Backend (`backend/src`)
- Express + `ws@8` в режиме `noServer`; `upgrade` роутит только `/ws`, остальные пути — `socket.destroy()` (`index.ts:66–75`).
- `GameServer` (`servers/gameServer.ts`, 160 строк): `join` / `action` / `leave`, `Map<WebSocket, playerId>`, broadcast **всем** клиентам без комнат. `handleAction` — **заглушка** (комментарий L135–137: серверная обработка действий не реализована).
- Комнат, сессий матча, seed'ов, heartbeat, лимита `maxPayload` — **нет**.
- REST: `/api/score` (scoreService + RateLimiter 30/мин/IP), `/api/health` (в т.ч. `wss.clients.size`).
- Инфраструктура прод-деплоя обкатана: docker compose, nginx-proxy `nginxproxy/nginx-proxy:1.11` (wss работает, проверено в проде), `TRUST_PROXY=1`.

### Frontend (`frontend/src`)
- **Ни одного WebSocket-клиента** — сингл-плеер полностью локальный; счёт уходит REST'ом.
- Движок `GameEngine` (`shared/engine/game-engine.ts`, ~680 строк) — **client-side**, управление через CQRS: команды `StartGame/Move/Rotate/SoftDrop/HardDrop/Hold/Tick(dt)/Pause/Resume`, читает UI через queries (`GetGameState/NextPiece/BoardState/Ghost`).
- Движок **почти портируем в Node**: в самом движке нет DOM/`window`; часы инъектируемые (input-слой использует `performance.now()` с фолбэком на `Date.now()`). DOM-зависимости только в `shared/input/touch.ts` (не нужен серверу).
- **Красная линия №1:** 7-bag в `shared/domain/pieces.ts:79` использует `Math.random()` — seed'а нет, детерминизма нет.
- **Красная линия №2:** у движка нет ни системы событий (только pull-queries), ни вставки garbage-линий; `clearLines()` вызывается только при локе (`game-engine.ts:530`).
- Тайминг: `Tick { dt }` — гравитацию считает движок, UI лишь сообщает elapsed time. Lock delay 500 мс/15 ресетов, DAS 167/33, очередь 3, SRS + wall kicks, A13 (`hitsPlacedBlock`) — всё уже в движке.
- Цикл: `GameView.vue` — rAF-цикл (`inputLoop`), `gameStore.handleCommand(actionToCommand(...))`.
- `shared/` живёт внутри `frontend/src` — backend его **не видит** (общего пакета нет).

### Инфраструктура WebSocket
- Dev: vite proxy `/ws → ws://localhost:3000` (уже настроен). Прод: wss через nginx-proxy, проверено встроенным клиентом node (SESSION_CONTEXT).
- nginx-proxy: конфиг генерируется docker-gen; **`proxy_read_timeout` по умолчанию 60 с** — idle-соединение без трафика рвётся. В контейнер приложения нужно добавить ws-ping (см. §5) или env таймаутов.
- Доки `ws` (context7, README): штатный паттерн heartbeat — сервер шлёт `ping` каждые 30 с, `pong` помечает `isAlive`, нетответивший — `terminate()`; клиент держит `pingTimeout = 30 с + запас` и `terminate()`. Backpressure — `ws.bufferedAmount` + `pause()/resume()`. `maxPayload` ограничивает размер входящего сообщения (по умолчанию 100 МиБ — для игры нужен порядок ~8–16 КиБ).

## 3. Главные разрывы «дизайн ↔ код»

1. **Seed-рандомайзер.** GDD требует `BagRandomizer(seed)` на клиенте и сервере; сейчас `Math.random()`. Нужен инъектируемый PRNG (mulberry32/xorshift32 + `crypto.randomInt` на сервере) и тесты на совпадение последовательностей.
2. **Общий `global_step` на комнату.** Фигуры раздаются циклически всем игрокам комнаты из одной последовательности — это ломает текущую per-player очередь движка (`fillQueue`/`spawnNextPiece`): очередь должна читаться из общего seed-стрима по индексу игрока.
3. **Garbage-вставка.** В движке её нет вообще: нужна команда вида `InsertGarbage(bitmask[])` (сдвиг стака вверх, «hold next» ~1 с — в GDD не описан, в гайдлайнах стандартен — решить), + визуал очереди входящей атаки (уже есть в renderer-слое место под HUD).
4. **События наружу.** Сервер считает атаку из `piece_lock { lines_cleared, ... }`, но и клиенту нужно видеть свою атаку/комбо/«ATTACK NULLIFIED». У движка только pull-модель — нужен либо emit событий лока, либо сервер шлёт все результаты и клиент рендерит из WS-потока (проще и честнее).
5. **Верификация `piece_lock`.** Буквальный GDD проверяет только `global_step`/`piece_type` — это защищает от подмены фигур, но не от «волшебного» стака: валидность x/y/rotation/линий сервер может проверить только **реплеем того же движка у себя** ⇒ движок всё равно обязан быть в Node.
6. **D1 (подпись результата)** — GDD-сессия матча естественно закрывает вопрос честности `POST /api/score`: результат выдаёт сервер матча, а не клиент.
7. **Общий код.** `shared/` нужно вынести в отдельный workspace-пакет (`packages/shared` или корневой `shared/`), иначе backend будет импортировать из `frontend/src` — tsconfig-костыль.

## 4. Риски и ограничения

- **Модель авторитетности не выбрана.** Буквальный GDD = клиент-авторитетный движок + серверная верификация. Альтернатива — сервер-авторитетный (клиент шлёт команды, сервер тикает движок и шлёт state) — контроль полный, но движок надо переводить на серверный тик и вносить нетворк-задержку в управление (исport/откат), что противоречит «движок владеет таймингом» и удорожает в разы.
- **Десинхрон** в клиент-авторитетной модели: такт гравитации идёт по локальным часам клиента; без общей `start_time`/коррекции стакана разъедутся. GDD задаёт `start_time = unix_ms + offset` — протокол пинга/замера RTT придётся добавить.
- **Один контейнер, память процесса:** состояние комнат живёт в памяти; рестарт деплоя убивает матчи. Для v1 приемлемо (окно деплоя), но нужен graceful: shutdown-событие «match_abandoned» + рейтинг не начислять.
- **Мобильные клиенты** (тач-ввод уже есть) — WS на мобильном интернете рвётся常: обязательны heartbeat + реконнект с восстановлением в матч (rejoin по токену) — в GDD этого нет.
- **nginx 60 с idle** — без ws-ping соединение тихо умирает посреди комнаты (не матча — комната стоит без трафика).
- **Объёмы трафика:** 2–4 стакана × ~200 событий/мин — мизер; `permessage-deflate` для state-сообщений бесплатен.

## 5. Технический задел (что делать в любом сценарии)

Независимо от выбранных решений в §6:
1. Вынести `shared/` в общий пакет; backend собирает движок из него (`tsx`/`tsc` project references).
2. Seed-рандомизатор в движке + тесты «одинаковая последовательность по seed».
3. Команда garbage-вставки + `lines_cleared` как событие.
4. WS heartbeat по докам `ws`: серверный `ping` 30 с + `terminate` нетответивших; клиентский `pingTimeout` (браузерный WebSocket пингов не умеет → прикладной `ping/pong` поверх JSON-протокола каждые ~25 с — держит и nginx idle заодно); `maxPayload: 16384`; лимит сообщений на соединение (свой RateLimiter переиспользуется).
5. Единый протокол сообщений (типизированный в shared): `room_*` (list/join/leave/ready), `game_start {seed, player_index, start_time}`, `piece_lock {global_step, ...}`, `attack_*`, `chat_*`, `ping/pong`.

## 6. Принятые решения (2026-11-02, ответы пользователя)

1. **Объём v1 = MVP:** комната по коду (доступ по коду/ссылке, без списка комнат и лиг) + 1×1 heads-up + garbage-атаки по `02_GAME_CONFIG.json` + чат комнаты. Протокол и модель данных сразу проектируются на 2–4 игроков (GDD-таргетинг top/all/random оставлен под будущее). За v1: список комнат/лобби, BO4, Shortlist(4), глобальный чат, зрители (04), Glicko-2/EXP (05).
2. **Авторитетность:** клиентский движок даёт отклик, сервер ведёт реплей на том же `GameEngine` в Node и валидирует каждый `piece_lock` полностью (`global_step`, тип, x/y/rotation, число сожжённых линий, корректность garbage-состояния). Рассогласование → дисконнект по GDD §2.3.
3. **Общий код:** отдельный workspace-пакет. `frontend/src/shared/*` → общий пакет (`shared/` в корне репозитория, npm workspaces уже есть); в общий пакет также переезжает будущий типизированный WS-протокол.

## 7. Порядок реализации (по принятым решениям §6)

Блок A: вынос `shared/` в корневой workspace-пакет + seed-PRNG (7-bag, uint32) + команда garbage-вставки + событие лока с `lines_cleared` — всё на существующих 220/49/46 тестах, сингл не страдает.
Блок B: сервер комнат MVP: код комнаты, state machine `lobby→ready→playing→over`, heartbeat (прикладной ping/pong + ws-ping), `maxPayload`, лимит сообщений; unit-тесты backend.
Блок C: `multiplayerStore` (WS-клиент: реконнект, rejoin по токену, app-level pong) + вьюхи комнаты/матча + визуал очереди входящего мусора.
Блок D: атаки 1×1 (формулы/задержки из `02_GAME_CONFIG.json`), серверный реплей `piece_lock`, результат матча сертифицирует сервер → честная запись в лидерборд (закрывает D1).
Блок E (вне v1): лобби/лиги, 4 игрока/BO4, зрители (04), Glicko-2 (05).
